# Chaza 작동 원리

인덱스·필터·검색 런타임의 내부 구조. 사용법은 [README](../README.ko.md), 포맷 전체 명세는 [SPEC.md](../SPEC.md) 참고.

## 아키텍처

```
빌드 시점                               런타임 (브라우저)
────────                               ─────────────────
corpus.json ─┐                          fetch(chaza.wasm)
chaza.json  ─┤                            │
             ▼                            ▼
        chaza CLI ──► chaza.wasm  ──► chaza.js 로더
       (runtime.wasm       │             ├─ 인스턴스화 (스트리밍 가능)
        패치)              │             ├─ chaza_index_ptr/len 글로벌 읽기
                           └─────────────┴─ set_index() → search()
```

런타임 WASM은 **한 번만** 컴파일되어 CLI 바이너리에 내장됩니다. 인덱스를 만들 때는 아무것도 컴파일하지 않습니다 — CLI가 코퍼스를 토큰화하고 필터를 만들어 인덱스 바이트를 런타임 모듈의 데이터 세그먼트로 패치해 넣을 뿐. 인덱스 빌드마다 Rust 크레이트를 생성·컴파일하는 tinysearch와의 핵심 차이입니다.

## 토큰화 파이프라인

생성기(native)와 런타임(wasm)이 같은 Zig 코드를 공유합니다 — 색인 시점과 쿼리 시점의 토큰 비트 일치를 명세 문서가 아니라 컴파일러가 강제합니다.

1. 소문자화 (ASCII A–Z)
2. 스크립트 그룹별 분절 (Latin, Hangul, Han, Hiragana, Katakana, Number). 같은 그룹의 연속 구간이 토큰 하나, 그룹 전환이 토큰 경계. 결합 문자는 앞 구간에 흡수.
3. 불용어 제거 (`--stopwords` 파일 제공 시)
4. 문서별 중복 제거
5. `choseong_search`가 켜져 있으면 초성 접두 토큰 추가 (마커 `\x01`, 길이 2~`choseong_max_len`; title 단어는 길이 1부터)
6. `prefix_fields` 소속 단어는 edge n-gram 접두 토큰 추가 (마커 `\x02`, 첫 2~8 코드포인트, 진부분 prefix만)
7. 다시 중복 제거

입력은 UTF-8 + NFC 전제. NFD(조합형) 한글은 초성 추출이 깨집니다.

### 불용어

내장 기본 리스트(영어 기능어 + 한국어 단독 어절 — 단독 검색어로 쓰일 만한 단어는 배제하도록 선별)가 CLI에 임베드되어 자동 적용됩니다. `--stopwords <file>`로 대체할 수 있고, 빈 파일을 주면 불용어 제거가 비활성화됩니다.

불용어는 **색인 시점에만** 제거됩니다. 목록이 번들에 포함되지 않아 런타임은 쿼리에서 불용어를 걸러낼 수 없고, 불용어는 어떤 문서와도 매칭되지 않습니다. 쿼리 일부가 불용어면 나머지 토큰으로 매칭되고(OR 랭킹), 전부 불용어면 결과가 비어 있습니다.

### 초성 토큰 (`\x01`)

한글 단어마다 앞 1~`choseong_max_len` 음절의 초성을 뽑아 `\x01` 마커를 붙인 토큰으로 추가합니다: 안녕하세요 → `\x01ㅇ`, `\x01ㅇㄴ`, `\x01ㅇㄴㅎ`. **본문 단어는 단일 자모 접두(길이 1)를 건너뛰어** 과도하게 넓은 매칭을 방지합니다 — `ㅇ` 하나만으로는 한국어 문서 거의 모두가 매칭되므로, 본문 초성은 길이 2부터 시작. title 단어는 길이 1을 유지해 단일 자음 쿼리로도 제목 매칭이 가능. 쿼리 시점에는 자모로만 이루어진 토큰에 같은 마커를 붙이므로, `ㅇㄴ`이 초성 ㅇㄴ으로 시작하는 단어가 있는 문서에 매칭됩니다. 검색 경로에 특수 분기 없음 — 마커 토큰도 일반 토큰처럼 조회됩니다.

### Prefix 토큰 (`\x02`)

`prefix_fields`(기본 `title`) 단어는 첫 2~8 코드포인트를 `\x02` 마커 토큰으로 추가 색인합니다: "programming" → `\x02pr` … `\x02programm`. 쿼리 시점에는 **마지막** 토큰(입력 중인 단어)만 exact와 `\x02` prefix를 병행 조회하고, 둘 중 하나만 hit여도 1 hit로 칩니다. 문서당 수십 바이트 비용으로 제목의 search-as-you-type이 되고, body 단어는 완전 일치를 유지합니다.

필터 수준의 prefix 조회는 불가능하므로(아래 참조) 색인 시점에 prefix를 토큰으로 실체화하는 것이 유일한 경로이며, 초성과 같은 수법입니다.

### Title 랭킹 토큰 (`\x03`)

title 필드의 토큰(과 그 초성 토큰)은 `\x03` 마커를 붙여 한 번 더 색인됩니다. 쿼리 시 모든 토큰을 `\x03` 버전으로도 조회해 `title_hits`를 세는데, 이는 **랭킹 전용** 신호 — `hits`나 JS API는 바뀌지 않습니다. `hits` 동점일 때 *제목*이 매칭된 문서가 본문-전용 매치·오탐보다 위에 옵니다 (`\x03` 토큰은 16비트 hi 필터에 있어, 가짜 title 신호는 두 독립 프로브를 모두 뚫어야 함: ~0.2% × 0.0015%). 1,000문서 코퍼스에서 known-item MRR@10을 0.38 → 0.98+로 끌어올렸고, 번들 크기 비용은 ~2%입니다.

## 필터: 전역 binary fuse filter 2개

모든 (토큰, 문서) 쌍을 코퍼스 전역 [binary fuse filter](https://arxiv.org/abs/2201.01174) 두 개에 넣습니다 — 정적 확률 집합:

- **lo** — 일반 + `\x01` 초성 토큰, 9비트 지문 (오탐 ~0.2%)
- **hi** — `\x02` prefix + `\x03` title 랭킹 토큰, 16비트 지문 (~0.0015%) — search-as-you-type과 랭킹에 쓰여 오탐이 사용자에게 직접 보이는 신호라 비트를 더 씀
- 조회당 정확히 3회 메모리 접근; 지문은 비트팩 저장 (폭 8~16, blob 헤더가 자기서술)
- exact membership 전용: 열거·삭제·prefix 조회 불가

v1.3까지는 문서마다 8비트 필터를 따로 만들었습니다. 문서 단위 규모에선 공간 낭비가 큽니다: fuse 크기 계수가 키 수백 개에선 ~1.45×인 반면 코퍼스 규모에선 ~1.15×이고, 문서당 28바이트 헤더와 세그먼트 반올림도 붙습니다. 전부 전역 필터 하나로 합치면서(엔트리 키 = `pairKey(doc_id, token_key)` — doc id를 splitmix64로 믹스해 토큰 키와 XOR) 필터 구역이 ~29% 줄었고, 그 절감분을 지문 폭에 재투자했습니다: 전송량은 그대로, 오탐은 절반, hi 계층은 사실상 정확 판정.

독립된 세 해시 층:

```
토큰 ─ xxhash64 ─► u64 키 ─ ⊕ splitmix64(doc_id) ─► 쌍 키 ─ murmur64(키 + seed) ─► 3개 위치 + w비트 지문
       (chaza 레벨)           (쌍 레벨)                       (필터 내부)
```

구성과 조회 모두 pure Zig (C `fastfilter` 레퍼런스 포팅, 지문 폭 일반화). 생성기와 런타임이 같은 코드를 공유하므로 빌드-쿼리 간 해시 불일치가 구조적으로 불가능합니다.

번들에는 필터만 저장됩니다 — 원본 텍스트나 토큰 목록은 남지 않습니다.

## 검색 실행

`search(query_ptr, query_len, max_results)`는 전부 WASM 안에서 실행됩니다:

1. 색인과 동일한 파이프라인으로 쿼리 토큰화
2. 초성 전용 토큰에 `\x01` 마킹, 마지막 토큰의 `\x02` prefix 프로브 생성
3. 쿼리 토큰 16개 상한 적용 (아래 참조)
4. 모든 문서에 대해 필터에 hit하는 쿼리 토큰 수(`hits`)와 `\x03` title 프로브 hit 수(`title_hits`) 계산
5. `hits ≥ 1` 문서만 후보, `hits` 내림차순 → `title_hits` 내림차순 → 문서 입력 순 정렬
6. `max_results`로 자르기 (0 → 20)
7. 결과 버퍼 반환: `[u32 count][(u32 doc_id, u32 hits) × count]`, little-endian

로더가 doc id로 문자열 풀에서 title / url / 메타를 꺼내고, 각 결과에 `hits`를 노출합니다.

### 왜 토큰 상한이 16인가?

OR 의미론에서는 토큰마다 모든 문서가 독립적으로 ~0.2% 오탐 확률을 가집니다. 토큰당 가짜 hit 기대치 ≈ N/512 문서. 상한이 없으면 아주 긴 쿼리는 전체 문서의 큰 비율을 잘못 매칭합니다. 16이면 최악에도 노이즈가 문서의 ~3% 수준이면서 현실적인 쿼리는 전혀 자르지 않습니다.

## 출력 포맷

`chaza.wasm`은 유효한 순수 WASM 모듈입니다. CLI의 wasm 패처(`src/wasm_patch.zig`)가 미리 빌드된 런타임 모듈을 섹션 단위로 재작성하며 LEB128 길이 헤더를 다시 계산합니다:

- **memory 섹션**: 인덱스 영역이 초기 메모리 안에 들어가도록 초기 페이지 수 확장
- **data 섹션**: 기존 메모리 끝(페이지 정렬)에 인덱스 바이트를 담은 active 데이터 세그먼트 1개 추가
- **global + export 섹션**: 인덱스 위치를 알리는 불변 i32 글로벌 2개를 `chaza_index_ptr` / `chaza_index_len`으로 export

로더는 모듈을 인스턴스화하고 — `WebAssembly.instantiateStreaming`이 동작하므로 다운로드와 컴파일이 겹칩니다 — 글로벌 2개를 읽어 `set_index(ptr, len)`를 호출합니다. 인덱스 바이트는 데이터 세그먼트를 통해 이미 wasm 메모리에 올라와 있어 로드 시점 alloc/복사가 없습니다. 쿼리용 `alloc`으로 메모리가 늘어나도 wasm 선형 메모리는 이동하지 않으므로 인덱스 영역은 계속 유효합니다.

인덱스 자체는 flat, 4바이트 정렬, little-endian 레이아웃(`[header][meta-names][doc-table][string-pool][filter-data]`, filter-data는 전역 blob 2개를 `[lo_len][hi_len][lo][hi]`로 보관)이고 런타임이 포인터 캐스트로 zero-parse로 읽습니다. 필드 단위 상세는 [SPEC.md](../SPEC.md) 참고.

## 실용적 규모 한계

세 개의 상한이 이 순서로 걸립니다:

1. **오탐 노이즈.** 쿼리 토큰당 가짜 결과 ≈ N/512. 문서 ~10,000개면 단일 토큰 쿼리의 기본 결과 페이지(20개)가 통계적 노이즈로 찰 수 있음. 이것이 실질 상한: **수천 문서** (chaza의 설계·검증 범위는 1,000문서까지).
2. **번들 크기.** 필터는 고엔트로피 바이트 — gzip이 거의 안 먹힘. 수천 문서면 수 MB 다운로드.
3. **CPU.** 검색은 선형 스캔 (문서 × 토큰 × 3 접근). ~10만 문서를 넘어야 문제 — 1, 2보다 한참 뒤.
